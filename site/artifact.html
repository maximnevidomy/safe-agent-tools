1safe-fetch Let an AI agent call any website or API.

Before: simple version (our baseline, not the original)
0%
After (safe-fetch)
100%

5 attack attempts. Score = share of attacks stopped.

The original idea

API Anything

From the tool library review: trust 60/100 · passed the library's security gate.
No flags in the library review. The risk below comes from the kind of tool, not from a finding in this repo.

The problem

A tool that fetches whatever URL the agent gives it can be tricked, by the agent or by text the agent read, into calling things on your own network: your laptop's admin pages, your cloud's secret-credentials address (169.254.169.254), internal services. This attack is called SSRF and it is one of the most common ways a fetch tool turns into a break-in.

What we changed

  • Allowlist of hosts by default, https only (the live demo uses a public mode: any public website, still https and port 443 only, with every private range blocked)
  • Every address a name resolves to is checked; private and reserved ranges are refused
  • The connection is pinned to the address that was checked (no DNS trick between check and connect)
  • Every redirect is re-checked from scratch
  • Size cap, time cap, per-caller rate limiter

  • A malicious page on an allowed host can still return hostile text: treat results as untrusted data
  • GET only; no proxy support

The original idea

FreeLLMAPI · also OmniRoute

From the tool library review: trust 60/100 · new (OmniRoute: trust 30).
Library review: code and data go to free providers, some of which train on it. OmniRoute: routes code to 200+ unknown free providers, leak risk.

The problem

A router that sends every prompt to whichever free provider answers also sends your private data there: client notes, emails, API keys pasted by accident. Free providers may store or train on it, and the router's own logs can become a second leak.

What we changed

  • Each provider declares the most sensitive data it may receive; requests declare how sensitive they are
  • Emails, phones, cards, tokens and keys are removed before anything leaves
  • Logs hold only provider, timing and counts, never the text
  • A circuit breaker stops hammering a dead provider
  • A 429 rests that provider for as long as it asked; per-provider requests-per-minute budgets; fast or reliable routing from observed results; sticky conversations; opt-in cache that never stores secret data

The original idea

Bybit trading-mcp

From the tool library review: trust 55/100 · rejected at the security gate.
Library review: exposes account-management tools including creating and deleting API keys and sub-accounts; last release more than 90 days ago.

The problem

If an agent can call tools that trade, withdraw or manage keys, then one confused instruction or one malicious web page can move real money. Reading prices does not need any of those powers.

What we changed

  • Only GET requests exist in the code; there is no write path to misuse
  • 18 read-only tools (market: tickers, candles, order book, funding, open interest, long/short ratio, recent trades, instruments, risk limits, insurance pool, volatility; account: positions, balance, orders, executions, closed PnL, fees, transaction log)
  • A fixed list of read-only tools; order, withdraw and key tools do not exist
  • Testnet by default; the real exchange needs an explicit double opt-in
  • At start-up the key is inspected and refused if it has trade or transfer rights

The original idea

Agent-Reach

From the tool library review: trust 70/100 · rejected at the security gate.
Library review: installed with curl; X, Reddit and Instagram work through account cookies, which risks bans and breaks terms of service.

The problem

Reading the web through a logged-in browser session means the agent holds your cookies, and scraping that way breaks the sites' rules and can get the account banned. Passing raw API answers or links straight to the agent also hands it private fields and dangerous links.

What we changed

  • Only legal channels: the official GitHub API and RSS
  • Repo names are validated, so '../../user' cannot reach another endpoint
  • Results are reduced to a whitelist of fields; only https links survive
  • Everything goes through safe-fetch
  • Works with no login: any public web page as clean text, YouTube channel videos, GitHub releases, Hacker News, Reddit (public feeds)
  • Repo audit: health score plus a static scan of the README, install scripts, workflows and source for dangerous patterns and committed secret files

The original idea

InstaMation

From the tool library review: trust 35/100 · new, very small project.
Library review: very young project (6 stars); needs checking that it uses the official API only.

The problem

A webhook is a public door. Without checking the sender's signature anyone can send fake messages, replays can make the bot answer twice, a flood can make it spam, and a bot that ignores 'stop' or talks over a human gets the account reported and blocked.

What we changed

  • Meta's HMAC signature is verified on the raw request bytes
  • Replays are dropped
  • Per-sender rate limit
  • 'Stop' is honoured and 'start' re-enables
  • Silent while a human has taken over
  • Message text is never stored

The original idea

CLI-Anything

From the tool library review: trust 75/100 · passed the library's security gate.
No flags in the library review. The risk below comes from the kind of tool, not from a finding in this repo.

The problem

Running a command built from text the agent wrote is the classic injection hole: one stray '&&' or ';' and the agent's text becomes a second command. The child process also inherits every secret in your environment, and a runaway command can print forever or never stop.

What we changed

  • Commands are chosen by name from an allowlist and mapped to absolute paths
  • No shell, so special characters are just text
  • Argument count, length and per-command rules
  • The child gets a clean environment
  • Hard timeout and output cap

The original idea

xerj

From the tool library review: trust 45/100 · rejected at the security gate.
Library review: installed with curl | sh from an unfamiliar domain, young repo with unusual star growth, optional reranking sends text to a third party.

The problem

An index that reads everything under a folder will also index your .env file, private keys, and anything a symlink points to outside the folder. Search results then hand those secrets to the agent, and a path like ../ can read files far outside the project.

What we changed

  • Never indexes .env, keys, credentials, symlinks, dependency folders or binary files
  • File reads are confined to the folder
  • Personal data is redacted in snippets
  • No network at all, nothing to install with a script

The original idea

clawscan · also vibe-shield

From the tool library review: trust 55/100 · passed (vibe-shield: trust 40).
Library review: both are young projects (about 150 stars or fewer). This tool is our own scanner for the same job, not a repair of a weak repo.

The problem

A skill is instructions plus scripts that your agent obeys. A poisoned one can pipe a download into a shell, hide orders in invisible characters, tell the agent to keep secrets from you, read your SSH keys or send files to a webhook.

What we changed

  • Static rules that flag pipe-to-shell, encoded payloads, destructive deletes, credential reads, known exfiltration endpoints, prompt-injection phrases and hidden Unicode
  • Verdict block, review or pass, with line numbers and a 0-100 safety score
  • Also catches typosquatted installs (a name one typo from express, requests...), NUL-byte hiding, compiled files, hidden comments aimed at the agent, long encoded blobs and wildcard permissions
  • Benign skills pass: 0 false alarms on the sample set

The original idea

37studio

From the tool library review: trust 50/100 · passed the library's security gate.
No flags in the library review. It auto-publishes to 9 platforms with your own keys; the risk below comes from the kind of tool.

The problem

A simple 'approved: true' flag is not enough. The text can be changed after approval, one approval can be reused, an old approval can be used days later, and an unsigned token can be written by the agent itself.

What we changed

  • Approval is a signed token bound to a hash of the exact payload
  • Single use
  • Expires after minutes
  • Signed with a secret the agent does not hold

The original idea

check-pre-lancamento

From the tool library review: trust 30/100 · rejected at the security gate.
Library review: no license (NOASSERTION), so it cannot be reused.

The problem

AI-built apps often ship with tables anyone can read or change, anonymous write access, policies that say 'true', functions that run with elevated rights, or a master key pasted in the code. A checklist that only greps for leaked keys misses most of this.

What we changed

  • Checks a LIVE website too: security headers, cookies, CORS, public /.env or /.git, service_role keys and secrets inside the page's scripts, public source maps, plus SEO, mobile and legal-page readiness, each with its own score
  • Reads your migrations, config and source
  • Flags tables without row level security, anonymous write grants, open policies, privileged functions without a fixed search_path, service-role keys and committed env files
  • Understands later fixes (an ALTER FUNCTION that repairs an earlier definition)
  • Ranks findings and gives a release verdict
